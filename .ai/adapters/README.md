# Travas de agente (hooks)

Regra escrita no `AGENTS.md` é um pedido: o modelo pode não seguir. Hook é código que roda **antes** da ação e decide se ela acontece, qualquer que seja o modelo. Aqui ficam as travas do padrão WCJ, uma configuração por ferramenta, todas derivadas das mesmas regras.

## O que cada trava faz

| Trava | Nega | Ainda permite |
|---|---|---|
| `rm-recursivo` | `rm -rf`, `rm -r`, `rimraf`, `xargs rm -rf`, inclusive dentro de `bash -c`, `$(...)`, `find -exec`, `ssh` e `uv run`; glob que não casa nada vale pela pasta onde seria expandido (`cd -P / && rm -rf *`), chaves fora de aspas se expandem (`rm -rf node_modules/{x,../app}`) e a pasta do `env --chdir` e do `sudo -D` vale | pasta regenerável (`node_modules`, `vendor`, `build`, `dist`, `public/build`, cache, log) e temporário fora do projeto |
| `git-force` | `git push --force`, `-f`, `+refspec`, `--mirror` | `--force-with-lease` **pergunta** ao humano |
| `git-reset-hard` | `git reset --hard` | `--soft`, `--mixed`, `git stash` |
| `git-clean` | `git clean -f` em qualquer combinação | `git clean -n` (lista sem apagar) |
| `segredo` | ler, copiar ou gravar `.env`, `.env.*`, arquivo com sufixo `.env` (`prod.env`, `deploy.env`) ou `.env-prod`, chave (`*.pem`, `*.key`, `id_*`), `~/.ssh`, `~/.aws`, credencial de ferramenta; `grep -r`, `rg -u` (lê o que o `.gitignore` esconde) e `rg -uu` que passariam pelo `.env` ou por uma chave, lidos com o filtro deles como a ferramenta lê (`--include`, `--exclude`, `--exclude-dir`, `-g`, `-t`, com `{a,b}`; no grep do macOS o padrão casa também com o caminho inteiro); `find -name '*.pem' -exec cat`; chaves que chegam ao segredo (`cat .{env,x}`); `dotenv list`, `get`, `set`, `dotenv -p` e o `dotenv` seguido de comando que imprime o ambiente (`printenv`, `env -0`, `sh -c printenv`), que imprimem ou gravam o `.env` (também como `dotenv-cli`); o mesmo passado como opção a `uv`, `poetry` e afins (`--env-file .env`, `--directory ~/.ssh`); `printenv`, `env`, `export -p` ou `declare -x` atrás de ferramenta que injeta ambiente (`doppler run -- printenv`); CLI de cofre que imprime o valor (`doppler secrets`, `op read`, `op inject`, `op item get --reveal`, `railway variables`, `heroku config`, `infisical secrets`, `infisical export`); `vercel env pull` para a saída padrão (`/dev/stdout`) ou para arquivo que a trava não reconhece como segredo, e `vercel project token`, `connect token`, `tokens add` e `ai-gateway api-keys create` | `.env.example`, `example.env`, `prod.env.example`; `ls`/`test`/`stat` no arquivo; `cp .env.example .env`; procurar o **nome** da variável no código; `rg` (respeita o `.gitignore`); `grep -r` com `--include` que deixa o segredo de fora (`--include='*.php'`) e `rg -uu -t php`; padrão entre aspas, que não é arquivo (`find . -name '*.env'`, `-g '!*.env'`, `echo '*.env' >> .gitignore`); chave passada com `-i` a `ssh`, `scp` e `sftp` (o comando cai em `producao` e pergunta); `vercel env pull` para o `.env.local` ou outro arquivo de variável (o de produção pergunta); `doppler secrets --only-names`, `op item get` sem `--reveal` |
| `banco-destrutivo` (Laravel) | `migrate:fresh`, `migrate:refresh`, `migrate:reset`, `db:wipe` e `migrate --force` fora do local: `APP_ENV` que não é local, `.env` carregado que é de produção ou que a trava não lê, `DB_HOST` de produção (também no `environment` ou no `env_file` do serviço do compose), via `ssh` ou `kubectl`, ou atrás de ferramenta que injeta ambiente | o mesmo com `APP_ENV` local, `testing` ou `e2e`, inclusive via `docker compose exec` e Sail |
| `banco-destrutivo` (Prisma) | `prisma migrate reset`, `migrate dev`, `migrate deploy`, `migrate resolve` (marca migração sem rodar), `db push` e `db execute` (SQL direto no banco) fora do local: URL com host de produção (`.agent-guard.json` ou `prod` no nome), `NODE_ENV=production`, via `ssh`, `kubectl` ou Docker remoto, ou URL que a trava não acha ou não lê (host que só existe depois de expandido, como `${DB_HOST}`). Host remoto sem sinal de produção (banco de dev na nuvem, socket do Cloud SQL) **pergunta** | o mesmo com a URL em `localhost`, socket da máquina, serviço do Docker (nome sem ponto) ou SQLite. Por `npx` (com versão, `prisma@6`), `pnpm`, `yarn`, `bun`, `npm exec`, `dlx` e `dotenv -e`. A URL vem da variável que o `prisma.config.*` ou o `schema.prisma` cita (padrão `DATABASE_URL`), do shell, do ambiente herdado pelo hook e dos `.env`; o host da autoridade e o `host` e o `hostaddr` da query contam todos (cada driver lê um), e lista de hosts conta host por host; valor que não é URL e vem de variável (`DATABASE_URL=$X`, `export` que pode não ter rodado) é ilegível; o `--url` do `db execute` vale mais que tudo (com `$VAR` só do que já estava exportado); a mensagem cita só o host |
| `banco-destrutivo` (Alembic) | `alembic upgrade`, `downgrade` (inclusive `base` e `-N`) e `stamp` fora do local: URL com host de produção (`.agent-guard.json` ou `prod` no nome), `ENVIRONMENT`, `APP_ENV` ou `ENV` de produção, seção, banco ou ambiente da ferramenta de produção escolhido pelo nome (`-n producao`, `-x db=prod`, `hatch -e prod`, `conda run -n producao`), via `ssh`, `kubectl` ou `oc` (`exec`, `run`, `debug`) ou Docker remoto (`--context`, `-H`, `DOCKER_HOST` ou `DOCKER_CONTEXT` que não são desta máquina), ou URL que a trava não acha ou não lê. Host remoto sem sinal de produção **pergunta** | o mesmo com a URL em `localhost`, socket da máquina, serviço do Docker ou SQLite; `--sql` (gera o SQL sem conectar); `current`, `history`, `check`, `revision`. Por `uv run` (com `--directory` e `--env-file`), `uvx`, `poetry run`, `pipenv run`, `pdm run`, `rye run`, `hatch run` (e `hatch env run`), `pixi run` e `pixi exec`, `pipx run`, `conda`, `mamba` e `micromamba run`, `python -m alembic` (e `python -Bm`, `pypy`, o lançador `py`, o Python sem GIL e o `.exe` do Windows), ferramenta chamada como módulo (`python -I -m uv run`), `dotenv -f`, contêiner (`docker compose run -e`, `-e VAR` que leva o valor do terminal) e script do `package.json`; opção que a trava não conhece na frente não esconde o Alembic. Conta a `sqlalchemy.url` do `alembic.ini` (ou do `-c`, do `ALEMBIC_CONFIG`, da seção do `-n`) quando o `env.py` a lê, e tudo o que ele cita (`os.environ`, `getenv`, `config()` do python-decouple, `env.str()` do environs, `settings.X` e objeto de settings com outro nome, como `app_settings.X`), lido do shell, do ambiente herdado pelo hook, dos `.env` (da pasta até a raiz do projeto, do `--env-file` e os citados no código), do padrão do `getenv` (texto ou a própria URL do ini) e do valor padrão da classe de settings, com e sem o `env_prefix` dela. Nome de banco (`DATABASE_URL`, `POSTGRES_URL_NON_POOLING`, `DATABASE_URL_SYNC`, `DB_HOST`, `PGHOST`) citado sem valor em lugar nenhum nega; variável ou campo com outro nome (`DB_CONNECTION`) conta quando o valor é URL de banco, e `REDIS_URL` e afins não contam. Campo calculado vale pelos atributos `*_HOST` e `*_SERVER` que ele usa e pela URL direta que ele prefere. Sem saber qual dessas o Python usa, todas contam: uma de produção ou uma que a trava não resolve basta para negar. `env.py` que troca a URL do ini (`set_main_option`, `section["sqlalchemy.url"] =`, dicionário com `sqlalchemy.url`, `create_engine`, `URL.create`) por algo que a trava não segue, ou que importa o engine da aplicação (nome `engine` ou `*_engine` importado de fora do SQLAlchemy, do SQLModel e do Alembic, `db.engine`, `get_engine()`), nega, porque a URL local que sobrou no ini não prova nada; `create_engine` com a própria URL do ini (direto, por `context.config` ou por variável que a recebe) não troca nada. Valor de nome de banco que não é URL (`DATABASE_URL=changeme`) é ilegível. `-x` com variável nega. `service=` do pg_service, `odbc_connect` e pyodbc sem banco (DSN do odbc.ini) são ilegíveis; Oracle e MSSQL com nome sem ponto (fora `localhost`), sem porta e sem banco são apelido; `sqlite+libsql` é banco na rede. Sem `env.py` achado (pasta, `pyproject.toml` ou recurso de pacote), nega |
| `producao` | (pergunta) `ssh`, `scp`, `rsync` remoto; `heroku run` (o texto inteiro, como o shell do dyno lê), `fly ssh console` e `railway ssh`, que rodam o comando no servidor; ferramenta que injeta ambiente com produção no nome do ambiente escolhido (`doppler run -c prd`, `railway run -e production`, `aws-vault exec producao`, `vercel env run -e production`; o valor de token e senha nunca volta na mensagem); comando que cita host de `.agent-guard.json` ou host com `prod` no nome, inclusive como opção de `uv`, `pipenv` e afins (`--index-url`); `--env=production`; `vercel --prod`, `vercel deploy --prod` ou `--target=production`, `vercel promote`, `rollback`, `redeploy` (a não ser com `--target` que não é produção), `alias` e `rolling-release` (também como `vc`, `npx vercel`, com `--team` antes do subcomando e com `--prod=false`, que a CLI lê como `--prod`); na mesma CLI, `vercel rm`/`remove`, `vercel api`, `vercel buy`, `vercel install`, `vercel env pull` e `vercel pull` de produção (`--environment=production`, `--prod` ou `--id` de deploy), e toda sub-ação que muda projeto, time ou conta (`env add`/`rm`/`update`, `project rm`, `domains rm`/`buy`, `dns add`/`rm`, `certs`, `blob del`, `cache purge`, `firewall publish`, `routes publish`, `teams invite`, `flags set`, `edge-config update`, `sandbox rm`…), com os apelidos da CLI (`domain`, `cert`, `team`, `webhook`, `mf`, `ln`); tudo isso também quando está no corpo de script do `package.json` (`npm run deploy`), menos a pista de `APP_ENV` e `--env` de produção, que em script é build (`webpack --env production`) | `curl` para localhost e para API pública; `vercel` e `vercel deploy` (preview), `vercel build --prod`, `promote status`, `rollback status`, `alias ls` e `rolling-release fetch`; as leituras dos grupos (`env ls`, `domains inspect`, `project ls`, `firewall rules list`, `flags list`, `api list`) e `switch`, `telemetry`, `link`, `logs`, `metrics` |
| `trava-protegida` | (pergunta) escrever em `.claude/settings*.json`, `.cursor/hooks.json`, `.codex/`, `.ai/adapters/`, `.agent-guard.json` | ler esses arquivos |

Valem para todas as travas:

- O comando de dentro de `doppler run`, `op run`, `dotenvx run`, `infisical run`, `aws-vault exec`, `railway run`, `direnv exec`, `vercel env run`, `heroku run`, `fly ssh console` e `railway ssh` passa por elas (`doppler run -- rm -rf app` nega), também com versão no `npx` (`npx dotenvx@latest run`). Opção que a trava não conhece não esconde o comando: o que vem depois do `--` também é analisado. Comando de banco atrás de ferramenta que injeta ambiente nega, porque a URL não aparece para a trava.
- Palavra reservada do shell não esconde o comando: `if [ -d app ]; then rm -rf app; fi`, `for d in app; do rm -rf $d; done`, `{ git push -f; }` e `! rm -rf app` negam como o comando sozinho.
- `cd` e `export` dentro de `( )`, `$( )`, `bash -c` ou no meio de pipeline não chegam ao comando seguinte. Os que podem não acontecer (dentro de `if`, `while`, `for` ou `case`, também depois de `time` ou `function NOME`; depois de `&&` ou `||`; no fim de pipeline, que o zsh roda no shell atual e o bash não; em sequência que vai para segundo plano) e o `cd` que falha (pasta que não existe nem foi criada antes no comando) abrem o mundo sem eles: cada comando seguinte passa pelas travas nos dois mundos, e vale o pior (`cd build; rm -rf *` nega se `build` não existe). O que depende deles com `&&` só roda no mundo em que aconteceram. No mundo sem o `cd`, pasta sem configuração do Alembic ou do Prisma não conta, porque a ferramenta falha sozinha. O motivo que só o mundo sem o `cd` ou o `export` dá vem com o pedido de encadear com `&&`; acima de 16 mundos, a trava pergunta.
- Opção curta junta ou com valor colado (`env -iS 'rm -rf app'`, `env -C..`, `sudo -uroot`), o `env -` (o `-i` do env), opção longa (`sudo --user`, `nice --adjustment`, `xargs --max-args`), `env -S`, o `=rm` do zsh e o `.exe` ou `.cmd` do Windows (`RM.exe`, `npx.cmd`) não escondem o comando.
- Nome do programa com maiúscula vale como o minúsculo (`RM -rf app`, `GIT push --force`): o APFS do macOS acha o binário do mesmo jeito. `cd`, `pushd`, `popd` e `export` são do shell e diferenciam maiúscula (`CD pasta` não muda a pasta), e atrás de `sudo`, `env` ou `doppler run` rodam em outro processo e também não mudam.
- Em `docker compose exec` e `run`, a trava lê o `compose.yaml`: o do `-f`, o do `COMPOSE_FILE` (do shell ou do `.env` da pasta do projeto) ou o da pasta e das de cima, com o override. A pasta de dentro do serviço sai do volume que cobre o `working_dir` (ou o `WORKDIR` do Dockerfile), do contexto do `build` e dos volumes, e contam todas em que a ferramenta acha a configuração dela. O ambiente de dentro é o do serviço: `environment` (com `${VAR}` trocado pelo shell de quem roda, atribuição na frente incluída), `env_file` (o último da lista vale mais) e `-e`; o ambiente da máquina só entra pelo `-e VAR` sem valor, que leva o valor do terminal.

A mensagem de bloqueio diz ao agente para **não contornar**: explicar ao humano o que queria fazer e deixar que ele execute. Se uma trava bloqueou algo legítimo, o conserto é aqui, com caso de teste, e não desligando a trava.

## Hosts de produção

Cada projeto lista os seus em `.agent-guard.json`, na raiz (o sync cria vazio):

```json
{ "hostsProducao": ["app.cliente.com.br", "203.0.113.10"] }
```

Todo comando que cita um desses hosts pede confirmação humana.

## Por ferramenta

| Ferramenta | Arquivo no projeto | Mecanismo | Cobertura |
|---|---|---|---|
| Claude Code | `.claude/settings.json` → `claude-code/hook.mjs` | hook `PreToolUse` em `Bash`, `Read`, `Edit`, `Write`, `MultiEdit`, `NotebookEdit`, `Grep` | todas as travas; `deny` e `ask`. Em modo "bypass permissions" o Claude Code aprova sozinho o que pede confirmação, então ali o `ask` vira `deny`. O comando em `settings.json` acha o hook mesmo sem `CLAUDE_PROJECT_DIR` e, se o hook quebrar, sai com 2: bloqueia em vez de liberar |
| Cursor | `.cursor/hooks.json` → `cursor/hook.mjs` | `beforeShellExecution` e `beforeReadFile`, com `failClosed` | todas as travas no shell; na leitura de arquivo, `segredo`. `beforeReadFile` não sabe perguntar, então o que pediria confirmação é negado. Escrita pela ferramenta de edição do Cursor não passa pelo hook |
| Codex | `.codex/config.toml` + `.codex/rules/wcj.rules` | política de aprovação `untrusted` (só leitura roda sem perguntar) + regras de execução | regra do Codex casa só o **começo** do comando, com maiúscula exata: não vê `--force` no fim, não sabe se o banco é local (pede confirmação), não tem allowlist de pasta regenerável (nega todo `rm -r`) e não lê script nem `compose.yaml`. O `.codex/config.toml` do projeto só vale com o projeto marcado como confiável no Codex |

O motor é um só, em `guard/` (Node sem dependência): `regras.mjs` é a entrada, `travas.mjs` tem uma função por trava, `shell.mjs` separa o comando e `caminhos.mjs` reconhece segredo. As ferramentas não divergem porque os adaptadores só traduzem a entrada e a saída de cada uma.

## Instalar

Projeto novo clonado do template já vem com tudo ligado. Projeto existente:

```bash
node scripts/sync-standards.mjs ../outro-projeto          # copia .ai/adapters e liga os hooks
node scripts/sync-standards.mjs ../outro-projeto --check  # falha se a versão estiver atrás ou alguma trava desligada
```

O sync acrescenta o hook em `.claude/settings.json` e `.cursor/hooks.json` sem apagar o que o projeto já tem. O Claude Code lê os hooks quando a sessão abre: depois de instalar, abra uma sessão nova.

## Testar

```bash
node --test .ai/adapters/guard/*.test.mjs
```

`guard.test.mjs` tem, para cada trava, o caso que ela nega e o caminho legítimo parecido que ela deixa passar. `adapters.test.mjs` roda cada hook como a ferramenta roda (processo separado, JSON na entrada) e confere que o projeto está com as travas ligadas. Os casos do `.gitleaks.toml` (segredo de assinatura escrito no código) rodam o binário do gitleaks quando ele está instalado ou em `GITLEAKS_BIN`; sem ele ficam pulados, e o CI os roda no job do gitleaks.

Para ver a trava disparando numa sessão real, ligue o registro: `WCJ_GUARD_LOG=/tmp/travas.jsonl`. Ele grava ferramenta, decisão e regra, nunca o comando (comando pode carregar segredo digitado).

## Limites

É trava contra acidente, não contra agente decidido a contornar. Ela não vê o que acontece dentro de script, alias, `composer` script, tarefa de `Makefile`, script do `pdm` (`pdm run <script>`), `poe` ou `taskipy`, ou programa que apaga por conta própria, nem variável de ambiente impressa fora de ferramenta que injeta ambiente (`printenv`) ou por outro caminho (`echo $DATABASE_URL`, `node -e 'console.log(process.env)'`), nem a exportada no perfil do shell. Para esses casos continua valendo a regra escrita (`.ai/core/`) e a revisão humana.

Script do `package.json` (`npm run`, `pnpm`, `yarn`, `bun run`, com `pre` e `post`) é lido pelas travas `banco-destrutivo` e `producao` (que só pergunta): `npm run deploy` com `vercel --prod` ou `rsync` para servidor dentro pergunta. As outras não olham o corpo: script é código que o humano escreveu, e carregar o `.env` no processo (`tsx --env-file=.env`) ou limpar pasta é o trabalho normal dele. Script rodado em servidor remoto (`ssh host "npm run ..."`) ou dentro de workspace (`-w`) não é lido; o `ssh` pergunta de qualquer jeito.

No Alembic a trava lê o `alembic.ini`, o `env.py` e a classe de settings que ele importa, mas não roda Python. URL montada no código sem atributo `*_HOST` ou `*_SERVER`, campo com alias, `secrets_dir`, cofre de segredo ou engine importado da aplicação ela não resolve, e o comando é negado: quem roda é o humano. Mas quando o `env.py` cita também uma fonte de banco que ela resolve, a URL montada ao lado (por função, cofre) não é vista, e ela julga pela fonte que achou. Variável com nome fora do padrão de banco (`DB_CONNECTION`) só conta quando a trava acha o valor dela. Quando o `env.py` lê a URL de uma variável de ambiente, direto ou por campo simples da classe de settings, a URL local passada no próprio comando conta (`DATABASE_URL=sqlite:///./dev.db alembic upgrade head`).

A trava também não enxerga o ambiente que outra ferramenta injeta (por isso o comando de banco atrás dela nega, e fora do banco ela só vê o comando), nem ferramenta desse tipo que ela não conhece (`chamber exec`, `envchain`, `sops exec-env`, que ficam como comando comum), túnel que faz o banco de produção parecer `localhost` (`ssh -L`, `kubectl port-forward`, `cloud-sql-proxy`), nem a variável que vem da imagem (`ENV` do Dockerfile). Sem volume e sem `build` no serviço, o comando de dentro do contêiner é analisado com os arquivos da pasta do comando; `compose.yaml` com `extends`, âncora ou merge de YAML ela não lê, e faz o mesmo. O `docker compose exec` roda num contêiner que já existe: a trava lê o `compose.yaml` de agora, que pode ter mudado depois do `up`. O contexto gravado por `docker context use` ela não lê: vale só o `--context`, o `-H`, o `DOCKER_HOST` e o `DOCKER_CONTEXT`. `DOCKER_HOST` por tcp fora do loopback (o `docker-env` do minikube, uma VM) conta como outra máquina. Do `dotenv`, a trava lê só as opções antes do comando. Variável exportada no perfil do shell só conta quando chega ao ambiente do hook.

No Alembic, o engine da aplicação é reconhecido pelo nome (`engine`, `*_engine`, `db.engine`, `get_engine()`): importado com outro nome, ele não é visto.

O contexto do Docker é julgado pelo nome: um contexto que o usuário criou com nome `orbstack` ou `colima-x` e que aponta para outra máquina passa como local.

Host sem ponto (`db`, `postgres`) conta como serviço do Docker, portanto local. Apelido curto do `/etc/hosts` ou do DNS interno que leve à produção só é pego com `prod` no nome ou listado no `.agent-guard.json`.

Busca recursiva que passa de 20 mil arquivos (sem contar `node_modules`, `vendor`, `.git`, `.venv` e pastas de cache) nega pedindo pasta menor: a trava não conferiu tudo.

A regra do Codex casa só o começo do comando: `alembic -c deploy.ini upgrade` e `vercel deploy --yes --prod` ficam com a política de aprovação `untrusted`, que pergunta. Projeto que afrouxar essa política perde essa cobertura.
